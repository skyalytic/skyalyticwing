# Wing Computer Use runtime integration

This document describes Wing's desktop adapter, observation lifecycle and input receipts. The extension owns this guide and supplies it with its registered tools. The extension manifest lists the session API and action confirmation guides for each platform.

## Real pointer and keyboard

Wing uses real OS mouse and keyboard input on Windows, macOS and Linux X11. There is no virtual mouse mode or mode setting. Old saved input preferences are ignored. `get_window_state` reports `inputMode: "physical"`. A desktop edge indicator, compact external control and the pointer accent indicate active control; user stop always wins.

Use the documented `sky` APIs through `node_repl`: obtain the returned app/window, activate it when needed, observe its screenshot, perform one input, then observe its result in the same cell. Do not turn that into separate model turns for the input and its screenshot. Reuse the returned window while valid; do not repeatedly enumerate all applications or request accessibility text when the screenshot is enough. Avoid narrating every click. Wait only when the observed UI is actually loading. A delivered input is not proof of success; never replay an uncertain action.

## Existing applications

Wing additionally supports `return_state: true` on `sky.click`, `sky.type_text`, `sky.press_key`, `sky.scroll`, and `sky.drag`. The adapter returns the resulting observation alongside the input receipt. It performs one input and returns the bound window's fresh screenshot/state in the same call; the image is delivered to the model automatically. Prefer `globalThis.state = await sky.click({window: globalThis.targetWindow, x, y, return_state: true})` when the next step needs visual feedback. Do not immediately capture the same state again. This does not permit a second state-changing input before the model inspects the result. `inputReceipts` retains delivered input if that observation fails. If a new modal or popup is the actual target, inspect the current window inventory and bind it explicitly instead of assuming it is the same window.

An empty `windows` array does not mean an application is stopped or logged out. `isRunning` reflects its process. Windows entries include hidden/minimized app windows, with `visible`, `minimized` and `bounds` fields; an application in the notification tray can still be logged in. Match the exact returned application executable, not just a window title (a helper process can use the same title). Several windows from one process can remain hidden: use their returned title and dimensions to select a candidate, then verify its actual screen. Do not assume a small login or auxiliary window is the signed-in main window.

For Windows, select an existing returned window, then `sky.activate_window` and take a fresh `sky.get_window_state`. Activation restores a hidden/minimized candidate; never infer that it is the main window or that login is required before inspecting its actual screen. `sky.launch_app` reuses a unique visible window, but refuses to guess among hidden/ambiguous windows when the application is already running. A hidden helper can have the same standard window styles as a main window. Candidate title, size and style are not proof of application state. Do not treat an auxiliary/blank window as the login state of the entire application.

Installed launcher paths can differ from running executable paths. `runningAppIds` reports matching executable candidates, including the same filename in the launcher's app/version subdirectories. Windows retain their actual `app` path and HWND/PID identity; never rebuild them with the launcher path. This generic package relationship is not proof of identity or login. If there are multiple processes/versions, inspect the actual UI rather than launching another instance or guessing which one owns a conversation.

## Visual desktop/tray fallback (all supported desktops)

If no main window is identifiable, a window cannot be restored, or a running app exposes only a tray icon, call `sky.list_windows()` and select one returned `kind: "desktop"` display. Each display is a real returned target (including the primary display with id 0). Pass that exact object to `sky.get_window_state({window: display})` for a full-display screenshot including its taskbar/tray. Desktop observations are visual only; do not request text-only accessibility. Inspect each relevant display rather than assuming the tray is on the currently focused monitor. Do not select the wallpaper/Program Manager window as a substitute for the full display.

Use screenshot coordinates with the same `sky.click`, `sky.scroll`, `sky.type_text`, and `sky.press_key` APIs: one observed action, then a new screenshot. Restore the app by its actually observed Dock/taskbar/tray icon, expanding overflow if visible. Do not guess icon positions, window titles, or executable paths. If a tray menu opens, observe it before selecting its restore/open item. Refresh `list_apps`/`list_windows` after the app appears, select the main window and verify the app and account/recipient in its screen before continuing. No terminal, UIA, new process, or app-specific script is needed for this fallback. If the app cannot be found after visual inspection, ask the user for the missing information through the waiting tool; do not silently restart or re-login. An "already logged in" dialog is a reason to find the existing signed-in instance, not request another login.

On macOS/Linux, use the package's screenshot workflow to inspect and restore an existing app from its observed Dock/taskbar/tray icon. The same distinction between hidden and stopped applies.

## Observing input results and recovering cells

Physical window observations capture the visible screen composition, including owned search/menu popups. A popup may extend beyond the parent window, so use coordinates from the latest returned screenshot, not remembered offsets. The adapter maps image pixels to the physical display origin, including secondary and negative-origin displays. Do not adjust coordinates for DPI yourself. If an app uses an independent, unowned popup that is missing from the window view, inspect the relevant returned desktop display rather than typing again.

Input preserves the observed foreground window. It does not reactivate the parent before every click or keystroke, because that can dismiss a search popup. If focus changes, observe the current UI again; explicitly activate the selected app only when it actually needs activation, then observe before input.

When the exact intended result is already visible, verify its label/identity AND result category before clicking it. A web-search suggestion, query echo, recent search, or history entry is not a contact, file, or application record. Do not click a similarly named web suggestion to complete a local application task. Do not retype the query just to make the background search box look populated. A placeholder and a result popup may belong to different UI layers; an empty-looking background field does not prove failed input. If uncertain, observe once more without input; do not label live results as history without evidence.

The adapter briefly allows input-driven rendering before the next screenshot, preserves UI text in PNG where the transport budget permits, and requests high image detail. Repeating identical text in the same field within one minute is rejected before injection. Observing, activating, or clicking near the same point does not reset this protection. Ctrl+A only selects the existing text; it does not clear it. Type immediately after observing that selection to replace, or delete the selected text in a separate cell and then type. Clicking the field again cancels the selection and does NOT clear the duplicate-input protection. Backspace/Delete without select-all and Escape do not prove the field is empty. Navigating with Tab or clicking a different field permits a new entry. A rejected duplicate never means that the earlier input failed. Use results that already exist rather than repeatedly clearing/retyping. No app names or contact names are hardcoded.

`type_text` uses a normal OS paste chord for non-ASCII text on Windows to support custom text controls and input methods. The helper preserves the previous clipboard contents and restores them only while it still owns the clipboard; a concurrent user copy is retained. It never retries a possibly delivered paste. On macOS/Linux the native text transport is unchanged. Successful OS delivery still does not prove the application accepted or displayed the intended value.

`type_text` inserts text into the focused field; it does not replace existing text. A successful input receipt means the OS accepted the input, not that the search or business task completed. Do not append the same query again because the chat background is unchanged or accessibility reports only a Window/Pane. Custom-rendered fields and popups often have no usable accessibility value/focus information. Inspect the search field and result popup in the screenshot. If results are still loading, wait briefly (for example 300 ms), then obtain another observation without clicking, activating, or typing. After two inconclusive observations, inspect the full display or ask for the missing state instead of looping. To correct a query, first verify the actual field and contents, then deliberately select and replace the text in separate observed actions. Never repeat a send action whose result is uncertain.

Keep cross-cell state explicitly on `globalThis` (for example `globalThis.targetWindow` and `globalThis.state`); cell-local `const`/`let` variables do not survive. Perform one input per cell and then observe. `inputReceipts` distinguishes `delivered`, `unknown` (possibly partial), and `not_started`. A later error does not undo an earlier delivered input. Catching a desktop API error in JavaScript does not turn the tool result into success. If Ctrl+A was delivered and Delete was not started, refresh and finish that pending edit; do not click the field again and assume it was cleared. Do not replay the whole cell. After a recoverable JavaScript error, old observations are invalid but a previously returned `targetWindow` can be passed to `get_window_state` to revalidate its identity and obtain fresh state. A cleared/null `state` is not a window. After cancellation/reset or a replaced window, refresh the inventory instead. No error, timeout, or missing screenshot proves that an attempted input had no effect.

## Reading ambiguous text and grouped results

Preserve the user's exact spelling for names, identifiers, addresses and values. Do not normalize an unfamiliar name into a more common word. OS input delivery and visual recognition are separate evidence: a delivered literal is not proof of the field value, but an ambiguous glyph is not proof the input method changed it either. If they appear to disagree, inspect before editing. Never claim an input-method, DPI, monitor, or model-internal cause without evidence.

Read the visible result group headings and check the relevant group, even if it has only one row. Do not reclassify a contact/file/application row as a group-message hit merely because its label mentions a group or includes a qualifier. A secondary group's "contains" label alone does not establish whether it matches a member, name or message body. A web suggestion is not a local record. A plausible candidate in the correct category is a reason to open its ordinary detail view and compare the identity/title, not to report that no match exists. Opening a candidate for inspection does not authorize sending to it.

When small text or a conflicting result matters to the next decision, magnify the relevant label together with its group heading, or inspect another presentation such as the title/detail view. These checks are conditional, not mandatory extra calls for every clear field. OCR, if separately available, is supporting evidence and may share the same character errors; do not install or invoke it automatically on every name. Semantic oddity is a reason to re-check, never proof of a person's name. Do not use a fixed application/name/character blacklist.

Before saying "no match", inspect the relevant group and distinguish an empty result from loading, clipped rows or an unreadable label. Scope the conclusion to the visible results; do not claim a global absence from a partial screen. If challenged, collect new evidence before explaining. Keep concise internal checks; do not add long step-by-step narration or unnecessary user questions. Ask for a missing identity only when candidate inspection leaves genuine ambiguity.

### Wing image magnification

On Windows, the existing `get_window_state` also accepts Wing's optional `screenshotId`, `region` and `scale` fields. Use the latest state's screenshot ID and coordinates; keep the result heading in the crop when it matters:

```js
globalThis.state = await sky.get_window_state({
  window: globalThis.state.window,
  screenshotId: globalThis.state.screenshots[0].id,
  region: { x: 20, y: 30, width: 360, height: 160 }, // Choose from the observed image.
  scale: 3
});
globalThis.targetWindow = globalThis.state.window;
```

This reads the cached native frame without clicking, typing, or taking another screenshot. It returns a new image and ID; subsequent coordinates refer to that magnified image. It does not renew an expired observation or invent missing pixels. Do not reuse the previous image ID/coordinates. To return to a full view or check later UI changes, call normal `get_window_state({window})`. On macOS/Linux use `computer_use` action `zoom` with its latest screenshot ID and image region; that path takes a new observation.

### Local screenshot evidence

The tool saves the exact PNG/JPEG bytes prepared for the model under the edition's own user data directory, `diagnostics/computer-use`. Tool results include `screenshotFile` and `screenshotSha256`; matching JSON metadata records the session, screenshot ID, dimensions and capture/derived-image information. These are local diagnostic copies, not proof that a remote provider received or interpreted them correctly. No extra desktop capture or upload is performed. Model context and conversation text still exclude image base64.

The archive retains at most 200 images and 128 MiB, pruning entries older than 7 days on the next save. Only its own generated image/metadata files are pruned. If saving fails, `screenshotArchive: "unavailable"` is returned without changing the input outcome or retrying an action. Old sessions without saved images cannot be reconstructed. The archive implementation and this guide belong to the desktop tool extension.

## Waiting for the human

When authentication, phone verification, a permission prompt, or restoring an app actually requires the user, call `computer_use_confirm` with `purpose: "user_step"` and a concise question explaining the required action and asking them to reply when done. Call this tool outside the JavaScript cell. This wait remains pending until the user replies, cancels, stops the task, or the tool/service is closed. It has no execution deadline and does not repeatedly spend model tokens while waiting. A screenshot refresh sleep of a few seconds is not this wait. Do not submit a blocked final/task verification while you are waiting for a user action they can complete.

Do not operate authentication dialogs, ask for authentication secrets, or bypass verification. First check for an already signed-in main window so that an unnecessary login is not started. The desktop is released during the wait. `answered: true` means a reply arrived. `answer` contains the original user text (for example “好了”, “还没完成”, or a correction). There is no required confirmation word, no injected yes/no options for a user step, and no automatic `completed` flag. Interpret the reply before continuing; neither an arbitrary reply nor cancellation proves the step completed. After the reply, refresh the window inventory, select the current main window, and inspect a new screenshot. Recheck all relevant state; windows and focus can change while the user works. Continue only after the required state is observed. If it is still missing, report the observed condition and ask for the remaining step rather than claiming success.

For a message or other external action covered by confirmations.md, use `purpose: "action_confirmation"` (the default). Include the exact destination/content. For this approval purpose, the explicit 确认/取消 choices produce `approved: true/false`. A custom written answer is preserved with `approved: null`; interpret its meaning and scope, and do not treat an unclear answer as approval. A completed user step does not replace this separate action confirmation. Cancellation, no reply, or a stopped tool is never approval. If the user cancels or the wait service fails, preserve progress and state precisely what remains; do not silently restart the task or resend anything.
